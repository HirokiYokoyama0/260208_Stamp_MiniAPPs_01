## 0. 要旨

**家族（member_count≥2）ユーザーは、来院スキャン時のマイルストーン特典の自動生成が「1来院ぶん遅れる」。** 原因は [`app/api/stamps/auto/route.ts`](../app/api/stamps/auto/route.ts#L174) が `family_stamp_totals` を **profiles 更新より前**に読み、その値（＝スキャン前の家族合算）を**更新後の値と誤認**して判定するため。

- 影響：家族ユーザーで、直近マイルストーンの `reward_exchanges`（`available`）が**スキャン時に作られない**（次回スキャン、または患者が「交換する」を押した時に作られる）。
- **恒久的な付与漏れではない**：①次回スキャンで自動的に付与される（自己回復）／②特典画面の「この特典と交換する」で即オンデマンド生成される。
- **単身ユーザーは正常**（個人ベースで判定・付与）。
- **特典画面の表示は正しい**（家族合算を更新後に読むため）。ズレているのは「付与側の判定範囲」だけ。

## 1. 事象

**横山浩紀（診察券 123459 / `U5c70cd61…`）**、2026-09-26 14:25 のカメラQRスキャンで個人 **115→130（+15 premium）**。スタンプは正常付与。しかし本来同時生成されるべき **ms120・ms130（歯ブラシ）が `reward_exchanges` に0件**。ダッシュボード（特典交換履歴）に現れない。

## 2. 調査で確定した事実（本番DB 読み取り専用・2026-09-26）

### 2.1 プロフィール／家族構成

| 対象 | stamp_count | role | 備考 |
|------|-------------|------|------|
| 横山浩紀（U5c70cd61）| **130** | parent | 家族代表 |
| 横山スマホなしこ | **2** | child | 代理管理メンバー（line_user_id=NULL）|
| **family_stamp_totals.total** | **132** | — | member_count=**2**（現在値は正常）|

### 2.2 reward_exchanges（本人・16件）

- `milestone_reached` は **10〜110**（有効行 available/pending/completed の**最大＝110**）。**120以上は0件**。
- cancelled/completed/pending/available が混在（過去の重複サーガ・スタッフ操作の履歴）。

### 2.3 Vercelランタイムログ（14:25 のスキャン・`npm run logs --source serverless`）

```
👨‍👩‍👧 家族スタンプ合算でマイルストーン判定: 102 → 117
✅ QRスタンプ自動付与成功: U5c70cd61... (+15個 → 合計130個)
🔍 マイルストーン判定: oldStampCount:102, newStampCount:117,
   allMilestones:[110], existingMilestones:[110], newMilestones:[]
```

- **判定が 102→117**（家族合算）で走り、到達は110（既存）のみ → **新規なし**。
- ログの「117」＝**スキャン前**の家族合算（横山115 + こ2）。**実際の遷移は 117→132**（横山130 + こ2）で、ここに **120・130** が含まれる。

### 2.4 対照（単身ユーザーは正常）

同ログで単身ユーザーは個人ベースで正しく付与：
```
🔍 マイルストーン判定: userId:U957f98f..., oldStampCount:15, newStampCount:30, newMilestones:[20,30]
🎁 マイルストーン特典付与: 20スタンプ toothbrush / 30スタンプ toothbrush
```

### 2.5 副次観察（別件・データ衛生）

`milestone_history` は **10〜200**まで存在するのに `reward_exchanges` は110止まり＝**孤立した milestone_history（120〜200）**。過去のテスト/クリーンアップの名残で、`milestone_history` は「現在有効な付与」の信頼できるソースではない。**本バグの主因ではない**が整理候補。

## 3. 根本原因（コード）

[`app/api/stamps/auto/route.ts`](../app/api/stamps/auto/route.ts) の処理順：

```
L152  profiles を読む（stamp_count = 115）
L166  currentStampCount=115, newStampNumber=130
L173  if (family_id) {
L174    family_stamp_totals を読む  ← ★ profiles 更新より前（＝スキャン前の合算 117）
L181    if (member_count >= 2) {
L182      oldFamilyTotal = total(117) - amount(15) = 102   ← ★ 誤り
L183      effectiveStampCountOld = 102
L184      effectiveStampCountNew = total(117)               ← ★ 誤り（117を「付与後」と誤認）
        }
      }
L191  stamp_history を insert（トリガーで profiles 更新）
L215  profiles.stamp_count = 130 に UPDATE
L234  checkMilestones(userId, 102, 117)  ← 102→117 で判定 → 110のみ（既存）→ 何も付与しない
```

**バグの本質**：`family_stamp_totals`（L174）は **profiles 更新（L215）より前**に読まれるため、返る値は**スキャン前**の家族合算（117）。ところがコードはそれを**スキャン後**の合算とみなし、`old = total - amount` としている。結果、判定範囲が実際の `117→132` ではなく **`102→117`**（＝1スキャンぶん過去）にずれる。

### 3.1 なぜ「1来院遅延」になるか

各スキャンは「(現family - amount) → 現family」で判定するため、**常に前回スキャンの増分範囲**を見る。つまり：

| スキャン | 実際の家族遷移 | 判定された範囲 | 付与される | 取り残し |
|---------|--------------|--------------|-----------|---------|
| 前々回 | 87→102 | 72→87 | 80,… | 90,100 |
| 前回 | 102→117 | 87→102 | 90,100 | 110 |
| 今回 | 117→132 | 102→117 | 110(既存) | **120,130** |
| 次回 | 132→… | 117→132 | **120,130** | … |

→ 直近マイルストーンは**次回スキャンで自動付与される**（自己回復）。ただし患者が来院を止めると、最後の増分ぶんは自動生成されないまま（＝**特典画面の「交換する」ボタン頼み**）。

### 3.2 なぜ特典画面の表示は正しいのか

特典画面 [`AdultRewardsPage.tsx`](../components/(adult)/AdultRewardsPage.tsx#L70) は、ページ描画時に `family_stamp_totals` を**更新後（＝132）に新規で読む**（[L253-260](../components/(adult)/AdultRewardsPage.tsx#L253)）。`effectiveStampCount = 132` で `canExchange: 132 >= milestone` を判定するため、**120・130 を正しく「交換可能」表示**する。

→ **表示（更新後読み）と付与（更新前読み）で読むタイミングが違う**ことが、「画面には出るがDBに無い」現象の正体。**基準（家族合算）自体は表示・付与とも一致**しており、ズレはタイミングのみ。

## 4. 影響範囲と重要度

| 項目 | 内容 |
|------|------|
| 対象 | **家族 member_count≥2 のユーザーのみ**（単身は正常）|

## 5. 修正方針（未適用・提案）

読むタイミングの誤認を正す。**2案**（どちらも判定を正しい `117→132` にする）。

### 案B（推奨・最小差分：読み取り位置はそのまま、解釈を修正）

`family_stamp_totals`（L174）は「スキャン前＝旧」の値なので、それを old とし、new = old + amount とする。

```ts
// 現状（app/api/stamps/auto/route.ts 付近）
if (familyTotal && familyTotal.member_count >= 2) {
  const oldFamilyTotal = familyTotal.total_stamp_count - amount; // ← 誤り
  effectiveStampCountOld = oldFamilyTotal;
  effectiveStampCountNew = familyTotal.total_stamp_count;        // ← 誤り
}

// 修正案B
if (familyTotal && familyTotal.member_count >= 2) {
  // family_stamp_totals はこの時点で profiles 更新前＝スキャン前の家族合算
  const oldFamilyTotal = familyTotal.total_stamp_count;           // 旧（例:117）
  effectiveStampCountOld = oldFamilyTotal;                        // 117
  effectiveStampCountNew = oldFamilyTotal + amount;              // 117 + 15 = 132（付与後）
}
```

- 根拠：スキャン中に家族合算が変わるのは「本人の +amount」だけなので `new = old + amount` は厳密。
- 差分が小さく、`checkMilestones` / `grantMilestoneReward` は無変更。

### 案A（代替・より堅牢：更新後に読む）

`family_stamp_totals` の読み取りを **profiles 更新（L215）の後**へ移動し、`new = total（132）` / `old = total - amount（117）` とする。並行更新にも強いが、コード移動が伴う。

> **推奨は案B**（最小差分・厳密）。案Aは並行スキャンが多い環境向けの保険。

### 5.1 重複安全性

修正後、家族ユーザーに 120,130 等が新規付与されるが、[`grantMilestoneReward`](../lib/milestones.ts#L204) の冪等ガード（同一 user×reward×milestone の有効行があればスキップ）と `checkMilestones` の既存除外により**重複は生じない**。患者が先に「交換する」で pending 化していても、次回スキャン時は existingActive（pending）を検出してスキップする。

## 6. テスト計画

### 6.1 単体（判定範囲）

`effectiveStampCountOld/New` の算出について：

| ケース | family前 | amount | 期待 old→new | 期待 新規milestone |
|--------|---------|--------|-------------|-----------------|
| 家族・境界跨ぎ | 117 | 15 | 117→132 | 120,130 |
| 家族・跨がない | 122 | 5 | 122→127 | （なし）|
| 家族・50到達 | 145 | 10 | 145→155 | 150(POIC) |
| 単身（member<2）| — | 15 | 個人 115→130 | 120,130（個人）|

### 6.2 結合（本番同等）

- テスト家族（親＋代理子）で、親が +15 スキャン → `reward_exchanges` に該当 available が**当該スキャンで**作られることを確認。
- 連続スキャンで遅延しないこと（前回分の取り残しが出ない）。
- 冪等：同一スキャンの二重リクエスト／交換ボタン先行時に重複しないこと。
- 回帰：単身ユーザーが従来どおりであること。

### 6.3 本番検証（デプロイ後）

- `npm run logs -- --source serverless --since 1d | grep 家族スタンプ合算` で、`判定: X → X+amount` になっている（旧: `X-amount → X` でない）ことを確認。
- 対象家族ユーザーの `reward_exchanges` を照会し、当該スキャンで available が生成されたことを確認。
