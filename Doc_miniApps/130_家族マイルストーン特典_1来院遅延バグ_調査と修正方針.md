## 0. 要旨

- **バグは実在**：家族（member_count≥2）ユーザーは、来院スキャン時のマイルストーン特典の自動生成が**「1来院ぶん遅れる」**。原因は [`app/api/stamps/auto/route.ts`](../app/api/stamps/auto/route.ts#L174) が `family_stamp_totals` を **profiles 更新より前**に読み、その値（スキャン前の合算）を**更新後と誤認**して判定するため。
- **ただし今は直さない（§1）**：**家族機能は未リリース**＝本番に実ユーザーの家族は存在しない。困っている患者はゼロ。中核の付与パスを単独で触るのは**回帰リスクだけを負う**。→ **家族機能リリース時に、案B＋テストデータ掃除＋結合テストを1パッケージで対応**するのが最適解。
- 恒久損失ではない（単身ユーザーは正常・特典画面表示も正常・交換ボタンで即受領可）。孤立 `milestone_history` もテスト汚染でリリース時に掃除すれば消える。

## 1. 対応方針（確定・2026-09-26）：家族機能リリース時にセット対応

### 1.1 なぜ今直さないか

- **家族機能は未リリース** → 本番に「実ユーザーの家族」は存在しない。`family_stamp_totals` の4家族は**全てテスト設定**（横山と同類）。
- ∴ **今この瞬間、本番で困っている患者はゼロ**。単独ホットフィックスは、**中核パス（付与ロジック）を触る＝全員への回帰リスクだけ負う**ため非合理。
- 横山の孤立 `milestone_history`（120〜200／`reward_exchanges`=なし）も**テスト垢の産物**。リリース時のテストデータ掃除で消える＝恒久課題ではない。
- → **「未リリース機能のバグはリリース前に直す」**が最適解。緊急対応は不要。

### 1.2 リリース時チェックリスト（持ち越し・必ずセットで）

家族機能をリリースする際、以下を**1パッケージ**で実施：

- [ ] **① 案B を適用**：`family_stamp_totals` は profiles 更新**前**の値なので、`old = 読値` / `new = old + amount` で判定（1来院遅延の是正）。実装詳細は §6。**※案A（更新後に再読）は view 再読の遅延リスクを避けるため非推奨 → 案Bに一本化。**
- [ ] **② 存在判定は `reward_exchanges` の有効行ベース**であることを確認（`milestone_history` を到達判定に使わない）。これが守られていれば mh 汚染があっても付与は正しく動く。
- [ ] **③ `milestone_history` をクリーンにしてリリース**：本番投入前にテスト汚染（横山の 120〜200／rx=null 等）を掃除。以後 **mh は「信頼ソースにしない」方針を明文化**。
- [ ] **④ クリーンなテスト家族で結合テスト**（親＋実子・複数スキャナ含む）：
  - ⓐ 当該スキャンで `available` が生成される
  - ⓑ 連続スキャンで遅延しない（前回分の取り残しが出ない）
  - ⓒ 交換ボタン先行でも重複しない（`034` 部分ユニーク `uq_reward_active` で担保）
  - ⓓ 単身ユーザーの回帰なし
- [ ] **⑤ バックフィル不要**（新機能なので過去データ生成の必要なし）。

## 2. 事象

**横山浩紀（診察券 123459 / `U5c70cd61…`）**、2026-09-26 14:25 のカメラQRスキャンで個人 **115→130（+15 premium）**。スタンプは正常付与。しかし本来同時生成されるべき **ms120・ms130（歯ブラシ）が `reward_exchanges` に0件**。ダッシュボード（特典交換履歴）に現れない。

## 3. 調査で確定した事実（本番DB 読み取り専用・2026-09-26）

### 3.1 プロフィール／家族構成

| 対象 | stamp_count | role | 備考 |
|------|-------------|------|------|
| 横山浩紀（U5c70cd61）| **130** | parent | 家族代表 |
| 横山スマホなしこ | **2** | child | 代理管理メンバー（line_user_id=NULL）|
| **family_stamp_totals.total** | **132** | — | member_count=**2**（現在値は正常）|

> 本番の `family_stamp_totals` は**4家族すべてテスト設定**（横山と同類）。実ユーザーの家族はゼロ。

### 3.2 reward_exchanges（本人・16件）

- `milestone_reached` は **10〜110**（有効行 available/pending/completed の**最大＝110**）。**120以上は0件**。
- cancelled/completed/pending/available が混在（過去の重複サーガ・スタッフ操作の履歴）。

### 3.3 Vercelランタイムログ（14:25 のスキャン・`npm run logs --source serverless`）

```
👨‍👩‍👧 家族スタンプ合算でマイルストーン判定: 102 → 117
✅ QRスタンプ自動付与成功: U5c70cd61... (+15個 → 合計130個)
🔍 マイルストーン判定: oldStampCount:102, newStampCount:117,
   allMilestones:[110], existingMilestones:[110], newMilestones:[]
```

- **判定が 102→117**（家族合算）で走り、到達は110（既存）のみ → **新規なし**。
- ログの「117」＝**スキャン前**の家族合算（横山115 + こ2）。**実際の遷移は 117→132**（横山130 + こ2）で、ここに **120・130** が含まれる。

### 3.4 対照（単身ユーザーは正常）

同ログで単身ユーザーは個人ベースで正しく付与：
```
🔍 マイルストーン判定: userId:U957f98f..., oldStampCount:15, newStampCount:30, newMilestones:[20,30]
🎁 マイルストーン特典付与: 20スタンプ toothbrush / 30スタンプ toothbrush
```

### 3.5 副次観察（テスト汚染・リリース時に掃除）

`milestone_history` は **10〜200**まで存在するのに `reward_exchanges` は110止まり＝**孤立した milestone_history（120〜200）**。過去のテスト/クリーンアップの名残で、**mh は「現在有効な付与」の信頼できるソースではない**。→ §1.2-③（リリース前掃除）＋§1.2-②（到達判定に mh を使わない）で対応。

## 4. 根本原因（コード）

[`app/api/stamps/auto/route.ts`](../app/api/stamps/auto/route.ts) の処理順：

```
L152  profiles を読む（stamp_count = 115）
L166  currentStampCount=115, newStampNumber=130
L173  if (family_id) {
L174    family_stamp_totals を読む  ← ★ profiles 更新より前（＝スキャン前の合算 117）
L181    if (member_count >= 2) {
L182      oldFamilyTotal = total(117) - amount(15) = 102   ← ★ 誤り
L183      effectiveStampCountOld = 102
L184      effectiveStampCountNew = total(117)               ← ★ 誤り（117を「付与後」と誤認）
        }
      }
L191  stamp_history を insert（トリガーで profiles 更新）
L215  profiles.stamp_count = 130 に UPDATE
L234  checkMilestones(userId, 102, 117)  ← 102→117 で判定 → 110のみ（既存）→ 何も付与しない
```

**バグの本質**：`family_stamp_totals`（L174）は **profiles 更新（L215）より前**に読まれるため、返る値は**スキャン前**の家族合算（117）。ところがコードはそれを**スキャン後**の合算とみなし `old = total - amount` としている。結果、判定範囲が実際の `117→132` ではなく **`102→117`**（＝1スキャンぶん過去）にずれる。

### 4.1 なぜ「1来院遅延」になるか

各スキャンは「(現family - amount) → 現family」で判定するため、**常に前回スキャンの増分範囲**を見る：

| スキャン | 実際の家族遷移 | 判定された範囲 | 付与される | 取り残し |
|---------|--------------|--------------|-----------|---------|
| 前回 | 102→117 | 87→102 | 90,100 | 110 |
| 今回 | 117→132 | 102→117 | 110(既存) | **120,130** |
| 次回 | 132→… | 117→132 | **120,130** | … |

→ 直近マイルストーンは**次回スキャンで自動付与される**（自己回復）。ただし患者が来院を止めると最後の増分ぶんは自動生成されないまま（＝特典画面の「交換する」ボタン頼み）。

### 4.2 なぜ特典画面の表示は正しいのか（＝基準ズレは無い）

特典画面 [`AdultRewardsPage.tsx`](../components/(adult)/AdultRewardsPage.tsx#L70) は、描画時に `family_stamp_totals` を**更新後（=132）に新規で読む**（[L253-260](../components/(adult)/AdultRewardsPage.tsx#L253)）。`effectiveStampCount=132` で `canExchange: 132 >= milestone` を判定するため **120・130 を正しく「交換可能」表示**する。

→ **表示（更新後読み）と付与（更新前読み）で読むタイミングが違う**ことが「画面に出るがDBに無い」の正体。**基準（家族合算）は表示・付与とも一致**しており、ズレはタイミングのみ。

## 6. 修正方針（案B・リリース時に適用）

読むタイミングの誤認を正す。`family_stamp_totals`（L174）は「スキャン前＝旧」の値なので、それを old とし、`new = old + amount` とする。

```ts
// 現状（app/api/stamps/auto/route.ts 付近）
if (familyTotal && familyTotal.member_count >= 2) {
  const oldFamilyTotal = familyTotal.total_stamp_count - amount; // ← 誤り
  effectiveStampCountOld = oldFamilyTotal;
  effectiveStampCountNew = familyTotal.total_stamp_count;        // ← 誤り
}

// 案B（読み取り位置はそのまま・解釈を修正）
if (familyTotal && familyTotal.member_count >= 2) {
  // family_stamp_totals はこの時点で profiles 更新前＝スキャン前の家族合算
  const oldFamilyTotal = familyTotal.total_stamp_count;           // 旧（例:117）
  effectiveStampCountOld = oldFamilyTotal;                        // 117
  effectiveStampCountNew = oldFamilyTotal + amount;              // 117 + 15 = 132（付与後）
}
```

- 根拠：スキャン中に家族合算が変わるのは「本人の +amount」だけなので `new = old + amount` は厳密。
- 差分が小さく、`checkMilestones` / `grantMilestoneReward` は無変更。
- **案A（更新後に再読）は非推奨**（view 再読の遅延／余分なクエリ）。案Bに一本化。

### 6.1 重複安全性

修正後、家族ユーザーに 120,130 等が新規付与されるが、[`grantMilestoneReward`](../lib/milestones.ts#L204) の冪等ガード（同一 user×reward×milestone の有効行があればスキップ）＋ `034` 部分ユニーク `uq_reward_active` により**重複は生じない**。患者が先に「交換する」で pending 化していても、次回スキャン時は existingActive（pending）を検出してスキップする。
